# Personal Money Manager Design

## Scope

Build a private, single-user, mobile-first money logger as one deployable TypeScript application. The React client supports login, quick entry, history, dashboard, and analytics. The Express API owns authentication, validation, persistence, time boundaries, and all authoritative financial calculations.

The product records three independent concepts: normal transactions, money lent, and money borrowed. It does not infer income or expenses, calculate a bank balance, add accounting categories, support multiple users, or require user-entered timestamps.

## Architecture

The repository is split into `client`, `server`, and `shared` modules. Vite serves the React client during development and Express serves both the REST API and the compiled client in production. Keeping both on one origin avoids cross-origin session-cookie complexity and fits local and Replit deployment.

`shared` contains Zod request schemas and API-facing types. The browser never imports server configuration or database modules. Server route modules delegate to focused services and repositories; only the database layer imports Drizzle.

```text
Mobile React client
       |
       | same-origin REST + HTTP-only session cookie
       v
Express API
  +-- authentication and session middleware
  +-- records: transactions, lent, borrowed
  +-- unified history
  +-- dashboard aggregation
  +-- analytics aggregation
       |
       v
Drizzle ORM / PostgreSQL driver
       |
       v
Neon PostgreSQL
```

## Authentication and Security

`POST /api/auth/login` compares the submitted password with `APP_PASSWORD` on the server using a timing-safe comparison. Development defaults to `2003`; production refuses to start without explicit `APP_PASSWORD` and `SESSION_SECRET` values. Successful login creates a random opaque session token. Only a SHA-256 digest of that token is stored in PostgreSQL; the token itself is placed in a signed, HTTP-only, same-site cookie. Sessions expire and can be revoked by logout.

All financial, dashboard, analytics, and history routes require a valid session. `GET /api/auth/me`, login, and logout are the only public authentication routes. Login uses an in-process IP-based limiter suitable for one Replit instance. Express trusts one proxy hop in production, sets security headers, rejects cross-origin state-changing requests, limits JSON body size, and never logs credentials or request bodies.

## Data Model and Money Rules

Drizzle migrations create `transactions`, `money_lent`, `money_borrowed`, and `sessions`. Financial IDs are UUIDs generated by PostgreSQL. Amounts use `NUMERIC(20, 2)` with database `CHECK (amount > 0)` constraints; timestamps use `TIMESTAMPTZ NOT NULL DEFAULT now()` and are indexed.

Amounts enter the system as strings, are validated with a strict decimal grammar, and leave the API as fixed two-decimal strings. More than two fractional digits are rejected instead of rounded. Values above the database precision are rejected. JavaScript `number` arithmetic is never used for money; SQL performs aggregates and `decimal.js` handles any application-layer decimal composition.

Descriptions and person names are trimmed, length-bounded, and required. Clients cannot provide IDs or timestamps on create operations.

## API and Data Flow

All responses use either `{ "success": true, "data": ... }` or `{ "success": false, "error": { "message": "...", "code": "..." } }`. Unknown resources return 404, malformed input returns 400, unauthenticated access returns 401, rate limits return 429, and unexpected failures return a sanitized 500.

CRUD routes expose create, list, detail, and delete operations for transactions, lending, and borrowing. Lists are newest-first and accept validated date filters. `GET /api/history` uses a SQL `UNION ALL` to normalize the three tables, filters by type and local-date range, orders deterministically by timestamp and ID, and paginates with bounded `limit` and `offset` values.

`GET /api/dashboard` computes today, current week, and current month in `APP_TIMEZONE`, converts boundaries to UTC for filtering, and returns SQL aggregates plus zero-filled daily series. `GET /api/analytics` accepts day, week, month, or year buckets and optional local date bounds. It returns chart-ready movement series, per-table statistics, and lending/borrowing person summaries. It never calculates an account balance.

## Timezone Handling

PostgreSQL stores every generated timestamp as an absolute UTC instant. `APP_TIMEZONE` is an IANA timezone and defaults to `Asia/Kolkata` in development. Date-only filters and dashboard boundaries are interpreted in that timezone with Luxon, then converted to UTC instants before database queries. API timestamps use ISO 8601 UTC strings; the React client formats them in the browser for display.

## Mobile-First Client

The client is a compact installable-style responsive web interface, optimized first for narrow screens. Authentication is cookie-based and checked through `/api/auth/me`; no credentials or session tokens enter local storage.

The primary navigation contains Dashboard, Add, History, and Analytics. Add uses three clear record modes with only the allowed fields. Dashboard cards preserve the three financial categories and use restrained comparison charts. History offers type and date filtering with deletion confirmation. Analytics offers period selection, movement charts, and person summaries. The client only formats returned values; it does not recompute authoritative totals.

## Error Handling and Operations

Startup validates environment configuration and reports a clear `DATABASE_URL` error rather than using mocks. `.env.example` contains names and safe placeholders only. Drizzle Kit provides generation and migration commands. Development runs Vite and Express concurrently; production builds both TypeScript targets and starts Express.

Server logs contain request IDs, status codes, and sanitized error context, without passwords, cookies, database URLs, or financial request bodies. Graceful shutdown stops accepting HTTP traffic and finishes outstanding work.

## Testing

Unit tests cover money validation, text normalization, local-time boundary conversion, and session-token hashing. API integration tests exercise authentication protection, login/logout, validation, record CRUD, history normalization, dashboard aggregates, analytics output, and sanitized errors against an isolated PostgreSQL database when `TEST_DATABASE_URL` is configured. Tests that need PostgreSQL fail with a clear configuration message rather than silently using mocks.

React tests cover login, entry forms, protected navigation, and rendering server-provided totals. Playwright smoke tests cover the main mobile flow against a configured test database. Verification includes type checking, unit/component tests, production build, migration checks, and live HTTP checks when Neon credentials are available.
